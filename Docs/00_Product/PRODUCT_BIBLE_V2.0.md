## 1. 产品定位与三大游戏模式协同

《赛马》（Frontier Derby）是一款以西部牛仔与纯血赛马为世界观的高品质竞技策略游戏。平台采用**统一经济底座（COIN 虚拟币）**，驱动三大逻辑独立但深度协同的玩法体系：

```
                              ┌───────────────────────────────┐
                              │     统一账户体系 (Account)     │
                              │     统一角色档案 (Player)      │
                              │   统一金币钱包总账 (Wallet)    │
                              └───────────────┬───────────────┘
                                              │
         ┌────────────────────────────────────┼────────────────────────────────────┐
         ▼                                    ▼                                    ▼
┌──────────────────┐                ┌──────────────────┐                ┌──────────────────┐
│ 模式一：经典下注盘 │                │ 模式二：街机与彩池 │                │ 模式三：马房与职业赛│
│ (Classic Parimutuel)              │ (Arcade & Jackpot)               │ (Ranch & Pro Derby)│
├──────────────────┤                ├──────────────────┤                ├──────────────────┤
│ - 固定 6 匹马轮换  │                │ - 二连碰冷热矩阵  │                │ - 幼驹/青年/成年养成│
│ - 独赢 (WIN)      │                │ - 二连单 (EXACTA)│                │ - 钉蹄理疗/马具装配│
│ - 连赢 (QUINELLA) │                │ - 位置盘 (PLACE) │                │ - G3/G2/G1 巡回锦标│
│ - 180s 极速竞猜   │                │ - 全服超级大奖池  │                │ - 纯血繁育/拍卖/P2P │
└──────────────────┘                └──────────────────┘                └──────────────────┘
```

1. **模式一（经典下注盘 - WIN/QUINELLA）**：
   - 定位：公共彩池轻度博弈与高频金币流转。
   - 节奏：固定 6 匹马、180 秒下注、15 秒准备、30 秒冲刺、5 分钟一轮，服务端权威生成赛果与赔率。
2. **模式二（街机四盘与超级大奖池 - ARCADE & JACKPOT）**：
   - 定位：高风险高回报的深度数字博弈。
   - 特色：二连单（精准冠亚军）、位置盘（前三）、全服动态滚存累积奖池。
3. **模式三（西部纯血马房养成、繁育与职业巡回赛 - RANCH & PRO DERBY）**：
   - 定位：长线资产沉浸、模拟经营与玩家间竞技（PvP/GvG）。
   - 核心：幼驹喂养（Foal）、青年调教（Juvenile）、成年装备与资质考核（Mature）、职业杯赛出征（Pro Racer）、公母配种孕育二代血统、全服拍卖行与私下点对点交易契约。

### 1.3 两个“马房”概念的业务隔离定义 (Sponsorship Club vs. Frontier Ranch)
为避免概念与代码实现冲突，平台严格划分两个层级的“马房”业务边界：
- **模式一·名驹赞助俱乐部 (Horse Sponsorship Club)**：
  - 路由与实体：`/api/stable/*`，数据表：`player_horse_stables`, `horse_dividends`；
  - 业务定位：模式一公共赛事的衍生轻度玩法。玩家认领 6 匹系统模板马并投喂胡萝卜，在该马赢得模式一比赛时享受头马出赛分红；
- **模式三·西部纯血马房与职业巡回赛 (Frontier Ranch & Pro Derby)**：
  - 路由与实体：`/api/ranch/*`，数据表：`ranch_horses`, `ranch_breeding_records` 等独立资产表；
  - 业务定位：玩家独占赛马数字资产。包含幼驹/青年/成年成长阶梯、五维属性与潜能封顶、穿戴装备、参加 G3/G2/G1 锦标赛、跨马房配种与拍卖行交易。

> **经济合规底线**：全部下注、饲育、装备、奖金与交易均为游戏内虚拟货币（COIN）。本产品不开放任何法币充值、现金提现、数字货币（USDT/BEP20/TRC20）、链上钱包或玩家私下免监管现金通道。

## 2. 全局产品架构与对象关系

平台统一确立严格的层级依赖与隔离边界，任何业务模块必须遵循以下流转链路：

$$\text{Account} \longrightarrow \text{Player} \longrightarrow \text{Wallet} \longrightarrow \text{Mode Data} \longrightarrow \text{Asset} \longrightarrow \text{Ledger / Audit}$$

### 2.1 实体对象职责界定

1. **Account（账号认证层）**：
   - 承载全局身份认证、JWT Session、设备指纹、安全风控、多端登录限制。
2. **Player（玩家角色层）**：
   - 承载跨模式通用数据：玩家 UID、昵称、等级、经验、VIP 声望、每日任务进度、成就、系统通知。
3. **Wallet（虚拟资产钱包）**：
   - 承载全平台统一流通货币（COIN）。
   - 维护 `balance`（可用余额）与 `frozen_balance`（冻结金额）。
4. **Mode Data（模式业务数据域）**：
   - 各模式拥有专属数据域，严禁跨模式直接读写内部私有表：
     - **Mode 1**：轮次（`rounds`）、注单（`bets`）、赛果赔率。
     - **Mode 2**：街机注单、彩池快照（`jackpot_pools`）。
     - **Mode 3**：马匹实体（`ranch_horses`）、训练与饲喂日志、职业赛事、拍卖竞价。
5. **Asset（玩家独有资产）**：
   - 涵盖职业赛马实体、马鞍蹄铁装备、道具、装扮。
   - 所有核心资产必须具备全服全局唯一 ID 与防伪证书编号（如 `WY-2026-XXXX`）。
6. **Transaction / Audit（资金账本与审计跟踪）**：
   - 记录每一笔资产与金币变动的完整前后快照。

### 2.2 核心设计与数据安全原则
- **模式业务解耦**：模式一、二、三的业务逻辑严禁直接操作 `Wallet.Balance` 字段。
- **账本强制驱动**：任何金币变动必须伴随一条且仅一条唯一的 `wallet_transactions` 流水记录。
- **严禁客户端决议**：禁止客户端上报最终余额或比赛名次，服务端为所有金币与数值计算的唯一权威源。
- **操作原子化**：资产划转、马匹过户与金币结算必须在同一数据库强一致事务中完成。

## 3. 经济系统与统一钱包账本规范 (Wallet Ledger)

### 3.1 钱包与账本持久化结构要求

#### 钱包表结构 (`wallets`)
| 字段名 | 类型 | 约束 | 业务释义 |
| :--- | :--- | :--- | :--- |
| `id` | BIGSERIAL | PK | 钱包物理主键 |
| `player_id` | BIGINT | UNIQUE NOT NULL | 归属玩家 ID (外键关联 players.id) |
| `balance` | NUMERIC(18, 2) | NOT NULL, CHECK(>= 0) | 可用金币余额 |
| `frozen_balance`| NUMERIC(18, 2) | NOT NULL, CHECK(>= 0) | 冻结金币（如拍卖竞价保证金） |
| `version` | INT | NOT NULL DEFAULT 1 | 乐观并发控制版本号 |
| `updated_at` | TIMESTAMPTZ | NOT NULL | 最后更新时间 (UTC) |

#### 账本流水表结构 (`wallet_transactions`)
| 字段名 | 类型 | 约束 | 业务释义 |
| :--- | :--- | :--- | :--- |
| `id` | BIGSERIAL | PK | 流水主键 |
| `player_id` | BIGINT | NOT NULL | 玩家 ID |
| `wallet_id` | BIGINT | NOT NULL | 钱包 ID |
| `business_type` | VARCHAR(32) | NOT NULL | 业务变更类型枚举 |
| `business_id` | VARCHAR(64) | NOT NULL | 关联业务实体唯一单号/业务ID |
| `direction` | VARCHAR(8) | NOT NULL | 流向：`INCOME` (+), `EXPENSE` (-), `FREEZE`, `UNFREEZE` |
| `amount` | NUMERIC(18, 2) | NOT NULL, CHECK(> 0) | 发生金额（正数） |
| `balance_before`| NUMERIC(18, 2) | NOT NULL | 变动前可用余额 |
| `balance_after` | NUMERIC(18, 2) | NOT NULL | 变动后可用余额 |
| `idempotency_key`| VARCHAR(128)| UNIQUE NOT NULL | 业务幂等键 (防重放、防网络重试) |
| `trace_id` | VARCHAR(64) | NOT NULL | 链路追踪 ID |
| `created_at` | TIMESTAMPTZ | NOT NULL | 创建时间 (UTC) |

#### 3.1.1 钱包表平滑升级方案 (Migration 014)
为支持拍卖行竞价资金原子冻结，系统通过增量迁移 `Database/DeployInit/014_wallet_frozen_balance.sql` 为现有 `wallets` 补充字段：
```sql
ALTER TABLE wallets ADD COLUMN IF NOT EXISTS frozen_balance NUMERIC(20, 2) NOT NULL DEFAULT 0.00 CHECK (frozen_balance >= 0);
COMMENT ON COLUMN wallets.frozen_balance IS '拍卖竞价等业务冻结资金，可用余额为 balance';
```

#### 3.1.2 账本流水表字段映射与向下兼容桥 (Compatibility Mapping)
针对当前代码库与数据库物理表的历史字段，服务层与 SQL 访问遵循以下映射桥接标准：
| 产品圣经逻辑字段 | 数据库现存物理字段名 | C# 实体对应属性 | 兼容规则与说明 |
| :--- | :--- | :--- | :--- |
| `business_type` | `transaction_type` | `TransactionType` | 逐步将存量字符串代码收敛至标准 20 种枚举 |
| `business_id` | `reference_id` | `ReferenceId` | 存储业务唯一单号或关联实体主键 |
| `trace_id` | `request_id` | `RequestId` | 全链路追踪 Trace ID |
| `direction` | - | - | 计算派生列：正数为 `INCOME`，负数为 `EXPENSE`；冻结操作在 `metadata_json` 记录 |
| `wallet_id` | - | - | 存量通过 `player_id` 关联 `wallets.player_id`；014 迁移可选补充并建立外键 |

### 3.3 交易执行核心六步原则 (Transaction Invariants)

任何引起金币与数字资产流转的用例，底层持久化必须严格按照单事务**六步法**执行：

```
1. Validate          2. Lock              3. Check Balance
[校验业务前置条件] ──> [行级锁定钱包账户] ──> [校验余额/冻结充足度]
                                                       │
6. Commit            5. Update Asset      4. Create Ledger     │
[提交数据库事务] <─── [执行业务资产转移] <─── [生成防重幂等流水] <───┘
```

> [!CAUTION]
> **严厉禁止的危险反模式**：
> 1. 先扣减数据库余额、后续业务逻辑发生异常却未配置完整回滚；
> 2. 先发放马匹/道具资产，后续写入账本失败；
> 3. 基于客户端本地传递的 `currentBalance` 判定逻辑或执行扣款；
> 4. 使用缺乏数据库唯一索引保护的“先查后插”假幂等设计。

  - 赛马达到 Lv.20，穿戴三件套马具并通过 400m 资格试跑考核；

  - 设立公马对外配种站赚取劳务费；通过拍卖行挂牌出售高潜能战马。

  - G1 顶级德比全服 12 强巅峰对决；
  - 三代名马系谱繁育，追求“传奇名驹神殿血统”隐性基因突破。

## 6. 安全、防刷与风控边界

1. **接口安全与防重放**：
   - 全平台写操作强制要求 `idempotencyKey` 与 `traceId`；
   - 客户端写操作请求频控（单玩家限流 5 次/秒），防止连点与脚本刷接口。
2. **交易与拍卖风控**：
   - **禁止低阶资产流通**：未成年马（Lv.1~19）及未过审成年马绝对禁止进入拍卖行与 P2P 交易；
   - **同 IP / 关联设备拦截**：严密监测拍卖出价者与卖家网络指纹，禁止自抬身价与自买自卖；
   - **血统反近亲退化**：算法强制阻断或重度惩罚三代内直系或旁系配种（潜能上限衰减 40%）。
3. **服务端随机权威**：
   - 比赛表现解算、饲料积食概率（25%）、遗传突变判定、毛色遗传完全由服务端加密随机数生成器决定并保留随机种子，客户端仅作回放呈现。
4. **后台操作合规审计**：
   - 管理后台涉及任何资产修正、补偿发放，必须提供经审批的 `operator_id`、工单号与 `reason`，入库持久化。
